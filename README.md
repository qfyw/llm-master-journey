## 设计说明

- **为什么用流式？** 用户体验的本质不是「总时长」，是「首字延迟」：整页返回要先空白好几秒，流式几百毫秒就出第一个字。模型本来就是逐 token 生成的，流式只是把过程露出来；代价是客户端要自己处理 delta 和拼装。
- **JSON 输出解决了什么？** 让程序能直接消费模型的输出——结构对了，`json.loads` 就能取货，不用肉眼看话。但 JSON 只保证「形状」合法，不保证「语义」正确（同一句话两次跑出不同的分钟数就是证据），所以程序端永远要有第二层字段校验。
- **一次对话大概花多少钱？** 实测一轮「system + 一句话 + 回答」约 42 输入 / 70 输出 token，折合 0.000644 元；即使按 1000 次对话算也不到 1 块钱。注意开了工具后输入明显变贵——工具说明书每轮都要重发，实测一次带工具的请求输入 339 token。

## 五个脚本，五级台阶

| 脚本 | 能力 | 一句话原理 |
|---|---|---|
| `week1/day01_hello.py` | 让模型响一声 | 一次请求 = SDK 发 HTTPS → 推理服务端 → 逐 token → SDK 拼装 |
| `week1/chat.py` | 多轮记忆 + 打字机 | 模型无状态：每次把**整个 messages 历史**重发，记忆在程序手里 |
| `week1/structured.py` | 结构化输出 | 提示词立合同 + `json.loads` 验收；保形状不保语义 |
| `week1/cost_log.py` | 重试 + 账本 | 错误分类：能修的睡 2 秒再试，修不好的别固执 |
| `week1/assistant.py` | 函数调用 CLI | 模型只「举手」，程序执行工具并把回执塞回剧本 |

## 第 2 周：健身助手 v2（Day 8-14）

> **第 2 周主题**：真实自用场景。不是 demo，是一个每天记录训练、能问历史、能周总结、还能看花费的小助手。

### 它能做什么

- **记录**：`今天卧推80kg 5组5次，跑步20分钟` → 模型解析成 JSON，程序验收后追加到 `week2/data/workouts.jsonl`
- **查询**：`我上次卧推多少？` / `这周练了几次？` → 模型只翻译意图，数据留在本地，由程序查
- **周总结**：`这周练得怎么样？` → 程序先算统计，模型只负责写点评
- **记账**：每次模型调用记录输入/输出 token、参考花费、耗时，按调用点归因
- **账单**：`bill_summary.py` 把本机账本变成可提交的派生账单，示例见 [bill-summary.example.md](week2/bill-summary.example.md)

### 三条模型调用线

| 线 | 模型做什么 | 程序做什么 | 输出 |
|---|---|---|---|
| 记录解析 | 把一句话解析成结构化记录 | JSON Schema 约束 + 语义验收 + 纠错 | 训练记录 |
| 意图翻译 | 把问句翻译成 `{"intent","exercise"}` | 查本地 `workouts.jsonl`、模板组装答案 | 历史回答 |
| 周总结 | 把统计 JSON 组织成 3-4 句点评 | 聚合本周训练数据、清洗给模型的字段 | 周总结 |

### 稳定性与成本

- 网络层只重试断网 / 408 / 429 / 5xx；401 / 402 / 400 直接失败，不空转
- 指数退避 2s → 4s；SDK 自带的 2 次隐藏重试已关闭（`max_retries=0`）
- 原始 `usage.jsonl` 是运行时数据，不入库；只提交派生账单 `bill-summary.md` / `bill-summary.example.md`

### 跑

```bash
python week2/assistant_v2.py
python week2/bill_summary.py week2/usage.example.jsonl week2/bill-summary.example.md
```
