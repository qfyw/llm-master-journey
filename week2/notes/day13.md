# Day 13 笔记

1. 错误分类：`RETRYABLE_STATUS` 里的 408/429/5xx 可以重试，401/402/400 不能。
   为什么「能修的错才重试」？401/402/400 是确定性错误——key 错、余额不足、参数/schema 错，重试多少次结果都一样；只有网络抖动、限流、服务端临时故障才值得再试。
   如果一个 401（key 错）也重试 3 次，用户实际要等多久、日志里会多出什么？按当前 `MAX_ATTEMPTS = 3`（总共试 3 次）算，中间只有 2 个间隔：2s + 4s = **6 秒**，日志里会出现 3 条失败记录。注意区分「总尝试次数」和「重试次数」：3 次尝试 = 2 次等待；如果是「首次之外再重试 3 次」（共 4 次），才是 2+4+8 = 14 秒。
   （把 Day 5 的「常见错误 → 处理方式」清单翻出来对照）

2. 两层重试叠在一起：OpenAI SDK 默认自己会重试 2 次，我们的 `ask_once` 又循环 3 次。
   最坏情况下一次操作实际发了几次 HTTP 请求？`max_retries=2` 是「首次之外再试 2 次」，所以每次 `create()` 最多 1 + 2 = 3 次 HTTP 请求；我们的循环 3 次 → 3 × 3 = **9 次**，不是 6 次。
   为什么今天要把 `max_retries` 设为 0？关掉 SDK 那层隐藏重试，让总次数回到我们可控的 3 次，退避节奏也由 `ask_once` 统一管理。
   另外，固定等 2 秒 vs 2s → 4s 的指数退避，区别在哪？固定间隔会在服务端还没恢复时反复撞；指数退避给服务端越来越长的恢复时间，也减少无效请求。
   生产环境为什么还要加 jitter（随机抖动）？很多客户端同时被限流时，如果都在「2 秒后」重试，会形成第二波拥堵（惊群效应）；在退避时间上加一个随机量（如 `2 ** n + random.uniform(0, 1)`），可以把重试打散，避免大家再次撞在同一时刻。

3. 今天的账本只记成功调用：失败/重试的成本去哪了？`track_usage` 只在拿到 `resp` 之后执行，失败、超时、断连的请求不会进 `usage.jsonl`；但服务端可能已经处理了输入、甚至生成了内容，照样计费。
   `bill-summary.md` 的合计和供应商真实账单可能差在哪？至少有：缓存命中折扣、峰谷价、隐藏推理 token、工具调用费用、失败请求的服务端计费，以及价格调整和四舍五入。所以本地账本是「参考价」，不是发票。

4. 账单按「日期」和「调用点」两个维度汇总，各能回答什么问题？按日期看「每天花多少、趋势如何、有没有异常日」；按调用点看「钱花在哪条链路、优化先动哪里」。
   用你生成的账单看一眼：总花费最高的是记录解析（0.003022，占约 43%）；但单次最贵的是记录纠错（0.001572/次），因为纠错请求要重发「原始提示词 + 上次错答 + 纠错消息」，输入有 402 token。
   如果下个月要把花费降一半，你先动哪条线、怎么动？先动记录线：提高首次解析成功率（few-shot / 提示词 / 字段设计），少触发纠错；其次压缩 JSON 输出和总结长度。意图翻译已经最便宜，不先动。

5. `usage.jsonl` 不进 Git，而 `bill-summary.md` 和 `usage.example.jsonl` 进 Git——三者的边界分别是什么？
   `usage.jsonl` 是原始运行时数据：有时间戳、调用点和我的使用习惯，每天变化，不是源码，所以 gitignore；`bill-summary.md` 是派生聚合，只保留日期 / 次数 / token / 花费，可以公开且可复现；`usage.example.jsonl` 是假数据，让别人 clone 后能跑通脚本。
   如果 example 文件里直接复制了真实账本，会泄露什么？泄露的是使用习惯：什么时候用、用哪条线、调用频率、token 量，结合时间戳还能推断作息和时区。
