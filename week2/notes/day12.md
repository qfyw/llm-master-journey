## 讲解（教练补充）

> 你上面的答案保留不动；这一节逐题对照，讲清楚哪里对了、哪里偏了、为什么。

### 第 1 题：两个账本差在哪

「Day 5 只有一个总 cost，现在把输入输出分开了」——只对了一半。Day 5 其实也按轮记了输入/输出 token 和本轮花费，它真正缺的是三样：

1. **持久化**：Day 5 的累加器在内存里，程序一退就归零；今天每条账写进 `usage.jsonl`，跨会话还在。
2. **逐次记录 + label**：Day 5 只有「本次会话总数」；今天每次调用一行，带 `label`（记录解析 / 记录纠错 / 意图翻译 / 周总结），能按调用点归因。
3. **耗时**：Day 5 没量延迟；今天每条账带 `latency_s`。

为什么按调用点归因更有用：总花费是一个乘积——`总花费 = 次数 × 每次 token × 单价`。只看总数，分不清是「查询太频繁」还是「总结输出太长」。有了 label，你能看到哪条线最贵、重试花了多少（记录纠错单独一个 label，失败成本不再隐身）、改 prompt 前后哪条线的账变了。**总账告诉你花了多少，归因告诉你该改哪里。**

### 第 2 题：耗时的四段，TTFT / TPOT

「输入信息，输出」太粗；文档拆成四段：

```
端到端耗时 = 网络与应用处理 + 排队 + Prefill + Decode
```

- **Prefill**：处理全部输入 token、建立 KV Cache，主要影响 **TTFT**（Time To First Token，从发请求到收到第一个 token）。
- **Decode**：一个接一个生成输出 token，主要影响 **TPOT**（Time Per Output Token）；生成阶段耗时 ≈ 输出 token 数 × TPOT。
- 端到端 ≈ TTFT + 生成阶段耗时。

你的 TTFT / TPOT 英文展开是对的。

**流式输出改善的是「等待感知」，不是真实计算**：它让 token 边生成边交付，用户更早看到内容；但它不减少 Prefill/Decode 的计算，也不让总时长消失。如果 TTFT 本身就高，流式救不了首字前的空白；如果 TPOT 慢，用户看到的是「挤牙膏」。

**今天的 `latency` 量的是整段，不是「输出用的时间」**：`perf_counter()` 包住的是非流式的 `client.chat.completions.create(...)`，从发请求到完整响应拼装完，包含网络 + 排队 + Prefill + Decode。要单独量 TTFT/TPOT，得开流式，在第一个 delta 和相邻 delta 之间打时间戳。

### 第 3 题：三行账与单价

你没把三行抄上来；用真实跑出来的数（我验收时用的临时数据，你自己的数会略有不同）：

| 调用 | 输入 / 输出 | 花费（元） |
|---|---|---|
| 记录解析 | 314 / 115 | 0.001548 |
| 意图翻译（上次卧推） | 240 / 33 | 0.000744 |
| 意图翻译（周总结） | 239 / 15 | 0.000598 |
| 周总结 | 232 / 75 | 0.001064 |

**哪条输出最多？不一定，看这次写了多少。** 这一轮记录解析 115 > 周总结 75，因为两个动作的 JSON 把 null 字段全写了一遍；但 Day 11 的周总结输出是 910，远超记录解析的 164。**别用直觉猜，账本就是用来替代直觉的。**

**输出单价是输入的 4 倍**：8 / 2 = 4，不是 3 倍。

**910 → 300 省多少**：少 610 个输出 token，610 × 8e-6 = **0.00488 元/次**（约 0.0049 元）。输入侧不变。注意这 910 里可能含隐藏推理 token，实际能压到多少要看任务；能直接控制的是回答长度和格式。

### 第 4 题：重试的成本

「重新加载输入、重新思考、输出」——方向对：**每次重试都是一个新的请求**，输入 token 要重发，输出可能重新生成，服务端已经生成的部分可能照常计费。补两个精确点：

1. **重试是 3 次总尝试，不是 1 次 + 3 次重试**：`for attempt in range(3)`。
2. **本地账本可能低估失败成本**：`track_usage` 只记录拿到 `resp` 的成功调用；如果请求到了服务端并生成了内容，但客户端超时/断连，账单上可能有、你的 `usage.jsonl` 里没有。所以「参考价」不是发票。

你列的公式对：3 次 × (1000 输入 + 500 输出) = 3000 输入 + 1500 输出：

- 输入：3000 × 2e-6 = 0.006 元
- 输出：1500 × 8e-6 = 0.012 元
- 合计：**0.018 元**

再补一条 Day 5 的原则：**能修的错才重试**（断网、超时、429）；401 key 错、402 余额不足，重试 3 次只是浪费时间。当前 v2 的 `ask_once` 对所有 `APIStatusError` 一律重试，下一步可以把 Day 5 的错误分类搬回来。

### 第 5 题：为什么 gitignore，GitHub 上展示什么

隐私是对的，但还有两个原因：**它是运行时数据，不是源码**（每天变，提交会让 diff 变成流水账）；**仓库应该装「能复现的东西」，不是你的私人使用记录**。

要在 GitHub 上展示「每天花多少钱」，提交**派生后的、脱敏的汇总**：

- 一个 `bill-summary.md` 或表格：日期 / 调用次数 / 输入 / 输出 / 参考花费；
- 一个生成它的脚本（读本地 `usage.jsonl` → 输出汇总）；
- 需要样例时，提交 `usage.example.jsonl`，里面是假数据。

**不要提交**：原始 `usage.jsonl`（时间戳、label、你的使用习惯）、原始 `workouts.jsonl`（训练数据）。`week2/data/` 整个已被 `.gitignore` 排除，这是对的。

### 文档对账三节（补全）

- **Token 不是字数，要以 Tokenizer 为准**：同一个意思，中文/英文/代码/JSON 切出来的 token 数不同；长 URL、UUID、转义 JSON 更耗 token。生产预算要用对应模型的 tokenizer 算，不能拿字数硬换算。今天的记录线就是例子：两个动作的 JSON 把每个字段（含 null）都写出来，输出 115 token，比一句中文长得多。
- **一次请求到底花多少钱**：`输入 token × 输入单价 + 输出 token × 输出单价 + 其它费用`（缓存、推理、工具）。我们按 2 元/M 输入、8 元/M 输出估算：记录 314/115 → 0.001548 元；查询 239/15 → 0.000598 元；总结 232/75 → 0.001064 元。输出单价是输入的 4 倍，所以长输出是账单大头。
- **延迟不能只看一个「总耗时」**：端到端 = 网络/排队 + Prefill + Decode；TTFT 看首字，TPOT 看后续生成速度。流式改善「等待感知」，不减少真实计算；今天的非流式 `latency` 是整段，不是纯 Decode。
