# Day 11 笔记

1. 本周总结这条链路里，「算」和「写」分别是谁做的？如果总结里的数字错了，该改哪一层？如果措辞很生硬，又该改哪一层？

   **算 = 程序**：`compute_week_stats` 在本周记录上做聚合（次数、最好成绩、累计组数/次数/分钟），`stats_for_model` 再把统计清洗成模型能正确读的副本。
   **写 = 模型**：`write_summary` 只拿到清洗后的统计 JSON，按 `SUMMARY_PROMPT` 的规则组织成 3-4 句人话。模型全程没见过 `workouts.jsonl`。

   分工决定故障归属：**数字错，先查统计层（程序），不是改提示词**——提示词改不了算术。只有「统计是对的、总结把数字说错了」才是生成层的问题。判断方法：把 `stats` 打印出来，和总结逐字对。**措辞生硬，才改 `SUMMARY_PROMPT`**（或换模型/调规则），那是措辞层的事。

2. 为什么「记录」和「查询意图」都套了 JSON Schema，而「本周总结」故意不套？

   看输出最终交给谁：**记录和查询意图交给程序解析**，形状必须硬保证——`strict` 合同挡住非法 JSON、缺字段、字段漂移；**周总结是终点，直接给人看**，不需要程序解析，套 schema 只会限制表达。
   但要注意两个精确说法：① schema 保的是**形状**，不是语义——Day 9 实测过形状 100% 合规却把日期编成 `2026-05-07`；② 总结的「自由」只指措辞，事实仍被锁死：`SUMMARY_PROMPT` 第 1、2 条要求只用统计里出现的数字/动作，数字的唯一来源是程序。

3. few-shot 和 JSON Schema 各管什么？为什么加了 few-shot 之后，程序端的验收（`is_valid` / 空列表判断）仍然不能删？

   **few-shot 管语义示例**：给模型看「这样进、这样出」——半小时→30、模糊输入→空列表；它教的是字段怎么填、边界在哪。
   **Schema 管形状和词汇表**：字段齐不齐、类型对不对、intent 只能是枚举里的词。

   两者都不是保证：few-shot 是**概率引导**，示例只能提高命中率；schema 只管形状，不管「空列表是否合理」「数字是否真实」。所以程序验收必须留——它是唯一对**内容成立不成立**负责的一层。三层各司其职：**示例教语义，契约管形状，程序做验收。**

4. 今天总结链路一次请求的输入 token 由哪几块组成？和昨天的查询链路比，它多了什么、少了什么？

   只有两块：**`SUMMARY_PROMPT`（固定规则）+ `stats_for_model` 生成的统计 JSON（可变材料）**。这条链路不是多轮对话，`messages` 里没有聊天记录——原始 `workouts.jsonl` 一条都没有上网。实测：**输入 215 / 输出 910**，按账本价约 **0.0077 元**。
   和昨天的查询链路（204 / 17，约 0.00054 元）比：输入几乎一样，都只有「规则 + 一段话」；今天的 user 消息从「问句」换成了「统计 JSON」（略大），规则也更长；**少了 schema 合同**（这次不约束解码）。真正的差别在**输出：910 vs 17**——总结要写字，而且多出来的 token 屏幕上看不见（模型的隐藏推理也计费）。总结贵约 14 倍，大头在输出。

5. 本周一条记录都没有时，为什么不把空统计直接交给模型「自由发挥」，而是程序先拦住？

   空输入 + 开放生成 = 最容易被编造的组合：没有事实可依，模型会补通用建议、虚构上周数据，甚至把「没有记录」包装成「练得少，继续加油」——用户会被误导。程序先拦，给出确定的事实（「这周还没有记录，练完说一句就有了」），既诚实又省掉一次没必要的调用。**诚实失败优于热情胡说。**
