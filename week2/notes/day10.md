# Day 10 笔记

1. 查历史为什么不让模型直接读 workouts.jsonl？**花费线性膨胀**：每条记录约 55 token，200 条就是 11,072 输入 token，是今天链路的 54 倍，而且每问一次都要重发一遍；**窗口有上限**：10 万条约 550 万 token，根本塞不进去；**信息越多越容易被带偏**（课文 92：信号被噪声稀释、新旧信息冲突、关键内容埋在中间）。结论：**检索/计算用程序，理解用模型**——数据留在本地，只有问题上网。

2. QUERY_SCHEMA 和 WORKOUT_SCHEMA 的共同点：都是 JSON Schema 合同——`strict: True`、每个字段都进 `required`、`additionalProperties: false`，都通过 `response_format` 递交给服务端。区别：WORKOUT_SCHEMA 产出 `exercises` 数组（记录），QUERY_SCHEMA 产出 `intent` 枚举 + 可空 `exercise`（指路）。

   在这条链路里，**模型只做一件事：把问句翻译成 `{"intent", "exercise"}`——它不看任何训练数据**。
   **程序做两件事：① `load_records` 读文件，`find_last` / `count_this_week` 查和算；② 模板把结果组装成人话**。数据查完不回流给模型。

3. `find_last` 用 `reversed(records)`：`save` 永远追加到文件末尾，所以越靠后越新，从后往前第一条命中就是「上次」。正着找会答成**最早**那次。「上次」包含今天——记录前后同问，答案从 11-04 80kg 变成 11-06 85kg。

4. 「这周」从**周一**算起；`date.today().weekday()` 在周一返回 **0**。把日期转成 `date` 对象更稳：字符串比较是逐字符字典序，不认日历——`"2026-1-5" > "2026-1-10"` 会得到 True（实际 1 月 5 日在前），`"2026-1-5"` 和 `"2026-01-05"` 也会排错；补零的 ISO 只是碰巧能用。`date` 对象比较有日历语义，能做减法（`today - timedelta(days=weekday())`），格式非法会立刻 `ValueError`。**让类型承担规则，别让字符串的巧合承担。**

5. 10 万条记录：① 会越跑越慢的是**本地部分**——`load_records` 每次提问都读全文件 O(n)，`find_last` 从尾扫到命中，`count_this_week` 全表扫 O(n)。② 不会变大的是**模型调用的输入 token**——查询线只有 `QUERY_PROMPT` + 问句（实测 204），记录线只有 `SYSTEM_PROMPT` + 一句话；历史根本不上网，所以 token 与历史长度无关。（A 方案另说：10 万条约 550 万 token，不是慢，是根本塞不下。）

## 今天真正记住的一件事

查数靠代码，理解靠模型——数据留在本地，问题才上网。

## 文档对账（context_engineering.md，2026-11-06）

- 第 39 节「上下文窗口不是输入框大小，是一整笔 Token 预算」：预算 = System Prompt + 工具 schema + few-shot + 多轮历史 + RAG 文档 + 工具结果 + 本轮问题 + **本轮输出**；公式 `输入 Token + 输出 Token ≤ 窗口`，每次请求重算，生产要预留输出空间。今天的实测正好是它的两种极端：查询链路固定 204 token（与历史无关），整包方案 200 条就 11,072。
- 第 92 节「为什么信息越多，模型反而可能答得更差？」：三个机制——**信号被噪声稀释**（十段材料一段有用）、**信息互相冲突**（旧规则 7 天 vs 新规则 15 天）、**位置效应**（Lost in the Middle：关键信息埋在中间容易被漏）。结论：**窗口装得下 ≠ 模型用得到**；上下文越长，每个 token 的边际价值越低（context rot）。幻觉是这些机制的下游症状。
