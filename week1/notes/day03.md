# Day 3 笔记

1. 昨天的 resp 是「整页写完装订好再交卷」；今天的 stream 是**连载**：服务器边写边寄，每集快递里只有新增的几个字（不是严格一个字一集，是一小撮字一集）；我的代码用 full 累加器边收边拼回整章。上行的 messages 仍然是**整包一次发**，流式只发生在下行的路上。

2. 新增字段名是 `piece.choices[0].delta.content`——**delta（Δ）= 增量**，这一集里新增的字，不是完整台词。它和整本的 `resp.choices[0].message.content` 同构，差别只有「完整台词 vs 新增量」。

3. `print(text, end="", flush=True)`：end="" 管**打印后不换行**（字才连得成句子）；flush=True 管**立刻上屏**（没有它终端攒着缓冲，打字机会一顿一顿地卡）。

4. 流式对用户体验的影响：**大幅降低首字延迟**。用户在意的不是总时长，而是「多久看到第一眼反应」——整页模式空白等好几秒，流式几百毫秒就出第一个字，等待从「猜测」变成「可感知的进度」。

5. 流式对成本统计的影响：**生成结束前无法结算**。输入 token 在发请求那一刻就定了，输出 token 要等最后一个字蹦完才知道，所以费用统计、余额扣减都发生在「完结」那一下（有的服务端会在最后一集快递里附带 usage 报数）。

## 今天真正记住的一件事
